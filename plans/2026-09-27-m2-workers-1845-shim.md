## Risks and edge cases

- **Earlier than the M1 plan intended** (hours, not a week). Mitigated: identical code path and
  version, guarded patch, one-at-a-time restarts with a smoke test between.
- **Restart drops in-flight requests** on that worker for the few minutes a 28 GB model takes to
  load. Staggering keeps the other worker serving.
- **The daily watchdog sync** would otherwise pull this change without restarting; pulling by hand
  and restarting now avoids a silent half-deployed state.

## Addendum (found during deployment, before any M2 restart)

`exec python "$SHIM"` changes the process's command line, and two things find servers by it:
m2-watchdog's wedge kill (`pkill -f 'mlx_lm[.]server.*--port N'`) and the dashboard's
`parseMlxProcesses` (keeps ps lines containing `mlx_lm.server`). Deployed as merged in #54, a
wedged M2 worker could not have been killed, and shimmed servers drop off the dashboard — the M1
orchestrator has been missing from it since 17:09.

Fix at the source rather than in each consumer: all three start scripts use
`exec -a mlx_lm.server python "$SHIM"`, so ps shows `mlx_lm.server <shim> --model … --port …`.
Verified on both Macs that the renamed interpreter still resolves its venv (`sys.prefix`,
`mlx_lm.__file__`) and that the watchdog's pattern matches and kills it. Guarded by
`tests/test_start_scripts_process_name.py` (fails on the #54 scripts). The M1 orchestrator needs
one more kickstart to pick up the name.
